# Data Dictionary

**All data in this directory is synthetic and illustrative — not real ODR
figures.** Generated with a fixed seed (`20260709`) so it reproduces
deterministically; see each role's `generate_*.py` script for the generator.

**Exception — real-data roles:** `opsgov_incidents` (documented below, not
under this directory) reads live from Postgres and does NOT carry the
synthetic-data marker (`ReportSpec.synthetic=False`). See CLAUDE.md's
real-data-role callout.

## `corporate_finance/`

FP&A quarterly business review data. Covers 14 fiscal quarters,
`2023-Q1` .. `2026-Q2`. Generated by `data/generate_corporate_finance.py`.

Enforced consistency spine (holds exactly, not just to float precision —
verified by an assertion at generation time):

```
gross_profit = revenue - cogs
ebitda       = gross_profit - opex_total
sum(segment_revenue.revenue for a period) == quarterly_pnl.revenue for that period
sum(opex_breakdown.amount   for a period) == quarterly_pnl.opex_total for that period
```

### `quarterly_pnl.parquet`

One row per fiscal quarter — the top-line P&A time series.

| Column | Type | Description |
|---|---|---|
| `period` | str | Fiscal quarter, e.g. `"2026-Q1"` |
| `quarter_start` | date | First day of the fiscal quarter |
| `revenue` | float ($M) | Total revenue |
| `cogs` | float ($M) | Cost of goods sold |
| `gross_profit` | float ($M) | `revenue - cogs` |
| `opex_total` | float ($M) | Total operating expense |
| `ebitda` | float ($M) | `gross_profit - opex_total` |
| `gross_margin_pct` | float (%) | `gross_profit / revenue * 100` |
| `ebitda_margin_pct` | float (%) | `ebitda / revenue * 100` |

### `segment_revenue.parquet`

Revenue broken out by business segment and subsegment. Sums to
`quarterly_pnl.revenue` within each `period`.

| Column | Type | Description |
|---|---|---|
| `period` | str | Fiscal quarter |
| `segment` | str | `Enterprise` \| `SMB` \| `Public Sector` |
| `subsegment` | str | `Software` \| `Services` |
| `revenue` | float ($M) | Revenue for this segment × subsegment |

### `opex_breakdown.parquet`

Operating expense broken out by category. Sums to `quarterly_pnl.opex_total`
within each `period`.

| Column | Type | Description |
|---|---|---|
| `period` | str | Fiscal quarter |
| `category` | str | `Salaries` \| `R&D` \| `Marketing` \| `G&A` \| `Other` |
| `amount` | float ($M) | Opex for this category |

### `budget_vs_actual.parquet`

Budget-vs-actual variance for the top-line items, one set of rows per
`period`. `favorable` is business-logic, not sign-based: a revenue/EBITDA
beat is favorable, a cost (COGS/Opex) *overrun* is unfavorable even though
its variance is positive.

| Column | Type | Description |
|---|---|---|
| `period` | str | Fiscal quarter |
| `line_item` | str | `Revenue` \| `COGS` \| `Opex` \| `EBITDA` |
| `budget` | float ($M) | Planned value |
| `actual` | float ($M) | Actual value (== `quarterly_pnl` for that line item) |
| `variance` | float ($M) | `actual - budget` |
| `favorable` | bool | Whether the variance is favorable to the business |

## `opsgov_incidents` (real data — Postgres, not a local file)

**REAL DATA, not synthetic.** Read live via
`odrkit.data.query_postgres_cached` (duckdb's `postgres` extension — no
psycopg2/sqlalchemy dependency). Credentials are never hardcoded: the DSN is
built by `odrkit.data.postgres_dsn_from_env("ODR_PG")` from `ODR_PG_HOST` /
`_PORT` / `_DATABASE` / `_USER` / `_PASSWORD` (or a full `ODR_PG_DSN`),
populated from a gitignored repo-root `.env` — copy `.env.example` to `.env`
and fill in real values. A missing/incomplete `.env` raises
`odrkit.data.MissingCredentialsError` rather than silently connecting with a
weak default. Source table:
`analytics.incidents_with_change_requests`. See
`odrkit/roles/opsgov_incidents.py` for the full shaping logic.

| Column | Type | Notes |
|---|---|---|
| `incident_id` | uuid | Primary key |
| `incident_number` | str | Human-readable id, e.g. `INC0000190` |
| `short_description` / `description` | str | Free text |
| `reporter_id` / `assignee_id` | uuid | People (no name/team dimension in this table) |
| `priority` | str | `"1 - Critical"` .. `"4 - Low"` — role normalizes to `Critical/High/Medium/Low` |
| `impact` / `urgency` | str | Inconsistent source casing (`"Medium"` vs `"medium"`) — role normalizes via `.str.title()` |
| `state` | str | `New` \| `In Progress` \| `On Hold` \| `Resolved` \| `Closed` |
| `ci_id` | uuid | Affected configuration item — no CI name/category dimension in this table |
| `caused_by` | uuid | Root-cause reference |
| `caused_by_change` | uuid, nullable | Populated 1:1 with `change_request_number` when a change caused the incident |
| `change_request_number` | str, nullable | e.g. `CHG0083` — presence is what the role calls "change-caused" |
| `created_at` / `updated_at` | timestamp | Role derives `resolution_hours = updated_at - created_at` for resolved/closed rows, and fiscal `period` (`YYYY-Qn`) from `created_at` |

**Known schema limitation that shapes several charts:** the table carries
only the *current* `state`, not a state-change history, so there is no way
to reconstruct a true historical backlog curve or a real stage-by-stage
funnel-conversion history. The role is explicit about this where it applies
(the "Backlog Bridge" and "Weekly Volume vs. Capacity Threshold" charts use
real, directly-computable quantities — opened/resolved/closed counts and
weekly opened volume — rather than a fabricated backlog-over-time series;
the "Incident Lifecycle Funnel" is captioned as a current-state snapshot,
not a conversion funnel).
